# 自动审查门禁

目标：长任务不需要用户逐个阶段发“帮我 review”，也能在每个阶段自动得到一次独立审查；同时不让“检查一下”这种日常词误触发。

## 何时自动审查

默认在以下时机自动执行：

1. 一个阶段/里程碑完成，准备进入下一阶段前
2. 一次较大的重构、删改、依赖升级之后
3. 正式交付前
4. 用户明确说“审查/复查/查 bug”时立即执行

不自动审查：

- 改一个错别字、文案、注释
- 只读探索、只查资料
- 纯配置查看（端口、路径、环境）
- 用户明确说“不用审查/跳过审查/只跑测试”
- 单个几秒钟就能完成的小改动（只跑测试即可）

## 触发词

### 强触发（立即做一次代码审查）

- 审查一下
- 审查代码
- 审查这版
- 帮我审查
- 代码审查
- 复查一下
- 复查逻辑
- 检查逻辑漏洞
- 检查有没有 bug
- 看看有没有安全问题
- 审一遍
- review 一下
- 帮我看看这段代码有没有问题

### 中触发（轻量检查，不默认启动完整审查）

- 检查一下
- 看看有没有问题

处理：先看有没有代码改动；有代码改动就审查改动，没有就只做普通检查，不启动完整多阶段审查。

### 不触发（明确排除）

- 检查配置
- 检查环境
- 检查文件是否存在
- 检查端口
- 检查网络
- 检查截图
- 检查一下进度
- 看看这个图片
- 看看日志
- 只是看看
- 不用审查
- 跳过审查
- 只跑测试

**“检查”单独出现不触发深度审查。**  
必须同时有代码/逻辑/改动/漏洞/bug 等对象，或明确说“审查/复查”。

## 审查流程

### 1. 先跑客观检查

- 构建
- 类型检查
- 测试
- 启动/核心路径
- 用户验收清单

把结果写进 `.noncoder/REVIEWS/<阶段>.md`。

### 2. 起 fresh reviewer

用 `subagent`，不要在主 Agent 上下文里“自己审自己”。

给 reviewer 的内容必须自包含：

- 目标
- 改动范围 / diff 或相关文件
- 验收标准
- 测试结果
- 约束（不能改什么）
- 只读要求

reviewer 的职责：

- 逻辑 bug
- 边界条件
- 回归风险
- 安全/数据风险
- 验收不符
- 明显的过度设计或死代码

不审：

- 命名喜好
- 格式/缩进
- 个人风格
- 与验收无关的“可以更好”

### 3. reviewer 输出

```text
VERDICT: PASS | FAIL
BLOCKERS:
- 文件:行号 — 问题 — 为什么是 blocker
MAJOR:
- ...
MINOR:
- ...
EVIDENCE:
- 相关测试/复现
```

要求：

- 不修改代码
- 不直接对用户长篇解释
- 用普通话写“会坏在哪”
- 无问题就明确 PASS，不要凑数

### 4. 主 Agent 处理

- BLOCKER：必须修，修完复测并重新审查
- MAJOR：能修就修；不能修写进风险报告
- MINOR：记录，不阻塞
- 最多 2 轮复审；仍 FAIL 就停下来报告，不要无限循环

### 5. 通过后

- 写 `.noncoder/REVIEWS/<阶段>.md`
- 在报告里写“已验证/未验证/无法验证”
- 才能进入下一阶段

## 复审规则

- 同一个 BLOCKER 连续两轮未解决：停止自动修复，报告根因和需要的决策
- reviewer 和主 Agent 意见冲突：以验收标准 + 可复现证据为准
- 不能因为“reviewer 说没问题”就跳过测试
- 不能因为“测试过了”就跳过审查

## 与 `/review` 插件的关系

`/review` 是手动深度审查入口，适合交付前或大改动。

自动阶段门禁不依赖 `/review`，用 `subagent` 完成；两者可以叠加：

```text
每阶段：自动 reviewer
交付前：/review 或 security-audit 深度审查
```

## 用户可见输出

不要给用户看原始 diff、堆栈、reviewer 的完整长文。

只汇报：

- 本阶段是否通过
- 必须修的问题（普通话）
- 已修/未修
- 下一步
- 日志路径

## 无 subagent 时

如果当前 preset 没有 `subagent` 工具：

- 做一次显式的“自我审查”清单
- 在报告里注明“未使用独立 reviewer，审查强度较低”
- 不假装做过独立审查
